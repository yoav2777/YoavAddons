### [medium] site-ui: Market search runs the 4.8 ms fuzzy search up to 3x per keystroke; one whole search only produces a boolean
- **detail:** In the shipped bundle at byte offset 697486 the Market page has two adjacent memos. The list memo calls `Fr(r,a)` on the filtered rows, and immediately after it: `x=(0,y.useMemo)(()=>a.trim()?Ir(t,a,1).fuzzy:!1,[t,a])`. `Fr` is defined at offset 289476 as literally `function Fr(e,t,n=1/0){return Ir(e,t,n).items}` -- so it already computes `.fuzzy` and throws it away, and the `x` memo then re-runs the entire search over ALL rows (`t`, unfiltered) a second time purely to read that one boolean. A third full search runs in the header dropdown (offset 311328, `Ir(n,e,8)`). None of this is debounced: `useUi.setQuery` fires on every keystroke (`onChange={(e)=>setQuery(e.target.value)}`, Header.tsx:122). Both Market memos also depend on `rows`, whose identity changes on every 30 s bazaar poll (`useRows` memo keys on `snapshot`, and `structuralSharing:false` guarantees a new snapshot object), so with an active query the whole thing re-runs every poll as well. Measured: a warm `fuse.search` over ~1.5k rows is 4.8 ms, so the fuzzy path costs ~15.7 ms per keystroke, of which ~4.8 ms is pure waste. This is on the typing path, where latency is most visible. Cold-vs-warm was only 1.26x (6.1 vs 4.8 ms), so the WeakMap cache miss caused by passing a freshly-filtered array to `Fr` is a minor secondary effect, not the main cost.
- **evidence:** Bundle index-KsTXbicp-v12.js @697486: `...},[t,o,e,c,u,f,m,a,g]),x=(0,y.useMemo)(()=>a.trim()?Ir(t,a,1).fuzzy:!1,[t,a]),S=(0,y.useRef)(null),C=so({count:v.length,...` Bundle @289476: `function Fr(e,t,n=1/0){return Ir(e,t,n).items}function Ir(e,t,n=1/0){...return{items:s,fuzzy:s.length>0}}` Benchmark (node, real notes/cache/bazaar.json -> 2197 rows, project's own fuse.js 7.5.0, keys ['name','search'], threshold .32, ignoreLocation true):   new Fuse(2197 rows) [index construction]  1.0 ms   fuse.search("hyperlon") warm index        4.8 ms   COLD new Fuse(out)+first search           6.1 ms  (cold/warm = 1.26x)   literal token scan over 2197 rows         0.1 ms   => per keystroke on the fuzzy path: 1 cold + 2 warm = 15.7 ms; typing 10 chars ~= 157 ms of blocked main thread For contrast, a whole bazaar poll (JSON.parse 3.6 MB + toProduct x2197 + useRows) is only 15.6 ms total.
- **suggested_fix:** Call `Ir` (searchRowsEx) once inside the Market list memo and keep both halves of its result -- e.g. have the memo return `{items, fuzzy}` (or stash `fuzzy` in a ref) -- then delete the separate `x` memo at @697486 entirely. That removes one full 4.8 ms fuzzy search per keystroke and per poll. Additionally debounce the search box by ~150 ms: keep `useUi.query` for the input's own value and feed a debounced copy into the two search memos (the codebase already has this pattern -- the AH search at bundle @379137 uses a `debounced` value with `enabled: debounced.trim().length>=2`, and AhItem.tsx:19 has the debounce hook). ### [low] mod: PriceScreen.loadToken and ahAsked are shared with the price-pool threads without volatile
- **detail:** C:/Users/Lenovo/Bazaar-Mod/src/main/java/com/yoav3577/bazaaranalyzer/PriceScreen.java:71 `private int loadToken;` is incremented on the render thread in load() (line 312) and read by the background task as the stale-response guard (lines 318 and 330). - **suggested_fix:** Declare `private volatile int loadToken;` and `private volatile String ahAsked = "";` (and `private volatile boolean triedNameSearch;`, which fallBackToNameSearch sets from the pool thread), or capture the token in a final local and compare against a volatile holder. One-line change, no behaviour change otherwise.

### [low] mod: Blocking file IO on the render thread in three trade paths, although an IO executor already exists
- **detail:** Capture already funnels its appends through a single-thread executor (Capture.java:18, 43), but three other paths write on the render thread: (1) TradeAhUi.click -> collect() -> AhTabs.append (TradeAhUi.java:113, AhTabs.java:243-256) does createDirectories + exists + size + writeString, plus an ItemReader.snbt NBT-to-string per item, inside the mouse-click handler; (2) TradeTracker.writeDebug (TradeTracker.java:241-254) runs from tick() and can additionally Files.move a 2 MB log; (3) PlayerTradeStore.add (PlayerTradeStore.java:41-53) writes the jsonl from tick() and re-merges the whole trade list first. ### [low] site-ui: A sold-list row hovered once keeps recomputing its craft cost every ~60 s forever

At 0.2-2 ms per recompute, hovering 30 rows costs roughly 6-60 ms of recompute plus 30 re-renders per minute, indefinitely.
- **evidence:** patch_v12.mjs:75 mounts sold rows with `lazy:!0` (the two eager mounts at :63 and :69 are single-instance -- auction detail page and the Lowest BIN card -- so there is no per-row explosion there). parts/20-listing-craft.js:188-196: effect deps `[want, ctx, tag, itemKey]`; :199 `const show = () => { clearTimeout(timer.current); setWant(true); setOpen(true); };` -- `want` is never reset. parts/00-shared.js:43-52 `BA_craftCtxFor(products, stamp)` returns a new object whenever `stamp` (= `q.data.lastUpdated`, see :65) changes; :15-17 `BA_CraftLstCache = new WeakMap()` keyed by ctx, so a new ctx = cold cache.
